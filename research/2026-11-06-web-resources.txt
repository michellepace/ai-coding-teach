## A. Client, server, HTTP

**A1. ✅ https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works**
- Title: "How the web works - Learn web development | MDN". Publisher: MDN (Mozilla).
- Covers clients vs servers, DNS, packets, an HTTP request and response, and URL parts. True beginner level. About 15 min.
- "Clients are the typical web user's internet-connected devices (for example, your computer connected to your Wi-Fi, or your phone connected to your mobile network) and web-accessing software available on those devices (usually a web browser like Firefox or Chrome)."
- "Servers are computers that store webpages, sites, or apps. When a client wants to access a webpage, a copy of the webpage code is downloaded from the server to the client machine, where it is rendered by the browser and displayed to the user."
- "The browser sends an HTTP request message to the server, asking it to send a copy of the website to the client."
- "If the server approves the client's request, the server sends the client a "200 OK" message, which means "Of course you can look at that website! Here it is", and then starts sending the website's files to the browser as a series of small chunks called packets."

**A2. ✅ https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Client-Server_overview**
- Title: "Client-server overview - Learn web development | MDN".
- Walks through GET and POST request/response examples, static vs dynamic sites, and what a web framework does. Beginner, but denser than A1 (raw HTTP headers). About 20–25 min.
- "Web browsers communicate with web servers using the HyperText Transfer Protocol (HTTP)."
- "When you click a link on a web page, submit a form, or run a search, the browser sends an HTTP Request to the server."
- "Web servers wait for client request messages, process them when they arrive, and reply to the web browser with an HTTP response message."
- This page has no standalone one-sentence definition of "client" or "server"; use A1 for those.

**A3. ✅ https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Introduction**
- Title: "Introduction to the server side - Learn web development | MDN".
- Explains what server-side code is for and why sites keep data in a database. Beginner. About 15–20 min.
- "Code running in the browser is known as client-side code and is primarily concerned with improving the appearance and behavior of a rendered web page."
- "By contrast, server-side website programming mostly involves choosing which content is returned to the browser in response to requests."
- "Most of the code to support a dynamic website must run on the server. Creating this code is known as "server-side programming" (or sometimes "back-end scripting")."

**A4. ✅ https://web.dev/articles/rendering-on-the-web**
- Title: "Rendering on the web". Authors: Addy Osmani and Jason Miller (Google, web.dev). Published February 6, 2019; last updated 2026-01-05.
- Intermediate. Assign only "Terminology", "Server-side rendering" and the rehydration section (about 8 min; whole article 15–20).
- SSR: "Rendering an app on the server to send HTML, rather than JavaScript, to the client."
- CSR: "Rendering an app in a browser, using JavaScript to modify the DOM."
- Hydration: "Running client-side scripts to add application state and interactivity to server-rendered HTML."

**A5. ✅ https://react.dev/reference/react-dom/client/hydrateRoot**
- Title: "hydrateRoot – React". Publisher: React team.
- A reference page, not a tutorial; assign only "Hydrating server-rendered HTML" (about 5 min).
- "Call `hydrateRoot` to “attach” React to existing HTML that was already rendered by React in a server environment."
- "Hydration turns the initial HTML snapshot from the server into a fully interactive app that runs in the browser."
- "The React tree you pass to `hydrateRoot` needs to produce the same output as it did on the server."

**A6. ✅ https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies**
- Title: "Using HTTP cookies - HTTP | MDN".
- The first two sections are beginner-friendly (about 8 min); the security sections are intermediate (about 20 min in full).
- "A cookie (also known as a web cookie or browser cookie) is a small piece of data a server sends to a user's web browser. The browser may store cookies, create new cookies, modify existing ones, and send them back to the same server with later requests."
- "Cookies enable web applications to store limited amounts of data and remember state information; by default the HTTP protocol is stateless."
- "After receiving an HTTP request, a server can send one or more `Set-Cookie` headers with the response, each one of which will set a separate cookie."
- React Router's own tie-in is B14 below.

## B. React Router v8, framework mode

### Version questions

- **Do the docs describe v8?** Yes. `https://reactrouter.com/home` is served from tag `react-router@8.5.1`; the changelog's top entry is v8.5.1 (2026-10-27).
- **Are URLs versioned?** Yes. `https://reactrouter.com/8.3.0/<path>` serves the docs as of that release, with the banner "Viewing docs for an older release". Titles carry the version, e.g. "Route Module v8.3.0 | React Router". Every path below returned 200 in both forms. The selector also lists 7.18.5, 6.30.6 and `main (unreleased)`.
- **Release dates (from the changelog):** v8.0.0 2026-06-17, v8.1.0 2026-06-29, v8.2.0 2026-07-08, v8.3.0 2026-07-22, v8.3.1 2026-08-27, v8.4.0 2026-09-15, v8.5.0 2026-10-19.

### What changed v7 to v8

**✅ https://reactrouter.com/8.3.0/changelog** (latest: ✅ https://reactrouter.com/changelog)
- "If you've adopted all active future flags in v7, then from a React Router API surface you're in good shape for v8."
- "We have now dropped `react-router-dom`, so if you didn't get around to swapping your imports in v7, you will need to swap them to `react-router` and `react-router/dom` for v8."
- "Use `loaderData` instead of `data` on `MetaArgs` and each item in `MetaArgs.matches`."
- "To modernize the library, React Router is now published as an ESM-only module"
- Minimums listed: "Node 22.22.0+", "React 19.2.7+", "Vite 7+". Middleware: "middleware is now always enabled".
- The 8.3.0 entry itself is mostly unstable RSC work and small fixes; nothing a beginner needs.

**✅ https://remix.run/blog/react-router-v8**
- Title: "React Router v8 | Remix". Author: Brooks Lybrand. Dated June 17, 2026. About 6 min.
- "The breaking changes for v8 are quite minimal, and all of them are changes you can make in v7."
- "we are officially marking React Router v6 and Remix v2 as End of Life (EOL)"

**✅ https://reactrouter.com/8.3.0/upgrading/v7**
- Title: "Updating from v7". For the teacher; a beginner can skip it.
- "In v8, you should import DOM-specific APIs from `react-router/dom` and everything else from `react-router`."

**Practical upshot for the student:**
- v7 framework-mode tutorials still apply almost unchanged.
- Any tutorial that imports from `react-router-dom` is out of date.
- `meta` receives `loaderData`, not `data`.
- Middleware and `context` are always on.

**B5. Actions: https://reactrouter.com/8.3.0/start/framework/actions**

### The four claims you asked for

1. **Where `loader` and `action` run:** B3 ("They are only called on the server when server rendering or during the build with pre-rendering.") and B5 ("Route actions defined with `action` are only called on the server while actions defined with `clientAction` are run in the browser.").
2. **Server-only code is removed from the client bundle:** B4 ("the `loader` function is removed from client bundles…"), B5 ("Server actions only run on the server and are removed from client bundles."), and B11.
3. **What `.server` modules are:** B10.
4. **SSR renders on the server, then hydrates in the browser:** B9, backed by B6. No single sentence in the React Router docs states this for route components in general; B9 is the closest official wording. Pair it with A4/A5 for the concept.

### D2. sqlite.org

All ✅, official, plain HTML.

**https://www.sqlite.org/about.html** ("About SQLite", about 3 min)
- "SQLite is an in-process library that implements a self-contained, serverless, zero-configuration, transactional SQL database engine."
- "SQLite is an embedded SQL database engine. Unlike most other SQL databases, SQLite does not have a separate server process. SQLite reads and writes directly to ordinary disk files. A complete SQL database with multiple tables, indices, triggers, and views, is contained in a single disk file."

**https://www.sqlite.org/serverless.html** ("SQLite Is Serverless", about 3 min; the clearest for this student)
- "Most SQL database engines are implemented as a separate server process."
- "With SQLite, the process that wants to access the database reads and writes directly from the database files on disk. There is no intermediary server process."

**https://www.sqlite.org/whentouse.html** ("Appropriate Uses For SQLite", 10–15 min)
- "SQLite does not compete with client/server databases. SQLite competes with fopen()."
- "SQLite works great as the database engine for most low to medium traffic websites (which is to say, most websites)."

**https://www.sqlite.org/wal.html** ("Write-Ahead Logging"; technical, assign sections 1–2 only, about 8 min)
- "The WAL approach inverts this. The original content is preserved in the database file and the changes are appended into a separate WAL file."
- "WAL provides more concurrency as readers do not block writers and a writer does not block readers. Reading and writing can proceed concurrently."
- "There is an additional quasi-persistent "-wal" file and "-shm" shared memory file associated with each database"
- "Unlike the other journaling modes, PRAGMA journal_mode=WAL is persistent."

**https://www.sqlite.org/tempfiles.html** ("Temporary Files Used By SQLite", sections 2.2–2.3, about 3 min; the best plain description of the two files)
- "The WAL file is always located in the same directory as the database file and has the same name as the database file except with the 4 characters "-wal" appended."
- "The shared-memory file, if it exists, is located in the same directory as the database file and has the same name as the database file except with the 4 characters "-shm" appended."
- "The shared-memory file contains no persistent content."

Local repo: `app/db/index.ts` sets `journal_mode = WAL`, and `data.db`, `data.db-wal` and `data.db-shm` sit in the repo root.

### D3. Drizzle ORM

**Version mismatch.** The current docs install `drizzle-orm@rc` and include an "Upgrade to v1.0" section. I found no versioned 0.x docs site. Two things differ from the codebase:

1. **Migrations layout.** Current docs show one timestamped folder per migration holding `migration.sql` and `snapshot.json`. The repo has the 0.x layout: `drizzle/0000_*.sql` plus `drizzle/meta/_journal.json` and `drizzle/meta/000N_snapshot.json`.
   - ✅ https://orm.drizzle.team/docs/upgrade-v1 lists the change as "removing `journal.json`" and "grouping SQL files and snapshots into separate migration folders".
2. **Relational query API.** The current page documents v2 (`defineRelations`).
   - ✅ https://orm.drizzle.team/docs/v0-v1-changes : "RQBv1 has been removed. Use Relational Queries v2 with the new `defineRelations()` API instead"
   - Local repo: a grep of `app/` found no `db.query.` or `relations(` calls. The codebase uses only the SQL-like API, so this topic can be skipped.

The init call also differs: the repo has the 0.x form `drizzle(getSqlite(), { schema })`, while current docs show `drizzle({ client: sqlite })`.

**Use the SQLite variants.** `https://orm.drizzle.team/docs/sqlite/<page>` shows `sqliteTable` examples; the unprefixed pages default to PostgreSQL.

All ✅, publisher Drizzle Team. Intermediate; readable after D1.

- **What Drizzle is: https://orm.drizzle.team/docs/overview** ("Drizzle ORM - Why Drizzle?", about 5 min)
  - "Drizzle ORM is a headless TypeScript ORM with a head."
  - "If you know SQL, you know Drizzle."
  - "Other ORMs and data frameworks tend to deviate/abstract you away from SQL, which leads to a double learning curve: needing to know both SQL and the framework’s API."
- **SQLite + better-sqlite3: https://orm.drizzle.team/docs/sqlite/get-started-sqlite** ("Drizzle ORM - SQLite")
  - "Drizzle has native support for SQLite connections with the `libsql`, `node:sqlite` and `better-sqlite3` drivers."
  - Shows `const sqlite = new Database('sqlite.db');` then `const db = drizzle({ client: sqlite });` (v1 syntax).

**How the journal works in 0.45 / 0.31.** I found no official prose docs for it, including in the pre-v1 docs source, which only draws a `_meta` folder. The primary sources that exist are teacher-level, not for the student:

- ✅ https://github.com/drizzle-team/drizzle-orm/discussions/2832 ("Migrations folder structure v3", by maintainer AlexBlokh, August 23, 2024). It shows the old tree with `meta/_journal.json` and says: "We have a journal which keeps track of migration snapshots as a linked list".
- ✅ https://raw.githubusercontent.com/drizzle-team/drizzle-orm/0.45.2/drizzle-orm/src/migrator.ts (source at tag 0.45.2).
  - `readMigrationFiles` reads `meta/_journal.json`, throws `Can't find meta/_journal.json file` if it is missing, and loads `<tag>.sql` for each journal entry.
  - It splits each file on `--> statement-breakpoint` and takes a sha256 hash of the SQL.
- ✅ https://raw.githubusercontent.com/drizzle-team/drizzle-orm/0.45.2/drizzle-orm/src/sqlite-core/dialect.ts (same tag).
  - `migrate()` creates `__drizzle_migrations` (`id`, `hash`, `created_at`) if absent and reads the most recent row.
  - It runs every migration whose journal `when` timestamp is newer than that row.
