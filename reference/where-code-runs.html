Reference sheet

Where code runs in Cadence

Code runs in two places. Data lives in a third. All three are on your machine.

Browser

Shows the page and reacts to clicks. The docs call it the client.

  • In Cadence: the tab at localhost:5173
  • Its console: F12, then Console
  • What it was sent: Ctrl+U

Server

Waits for requests and answers them.

  • In Cadence: the program npm run dev starts
  • Its console: the terminal it runs in
  • Stop it: Ctrl+C

Database

Where the data rests, running or not.

  • In Cadence: the file data.db in the repo root
  • Not in git. Only the server opens it
  • Rebuild the sample data: npm run db:seed

Where does it run?

Code Runs Why
A loader in app/routes/*.tsx Server React Router finds it by name and leaves it out of the code it sends to browsers.
The component a route file exports, such as Home Server then Browser The server runs it to build the HTML. The browser runs it again to make the page respond (hydration).
app/services/*.ts Server Services use db, the connection to data.db. Loaders call them.
app/db/index.ts Server It opens data.db.
data.db Database Not code. Tables of rows.
Also true, and coming up in later lessons
Code Runs Why
An action in app/routes/*.tsx Server The loader's twin, for saving a change. Left out of the browser's code in the same way.
Shared components in app/components/ Server then Browser Route components use them, so they run wherever those run.
Code inside useEffect(…), and click handlers Browser They only run once the page is live in a browser.
app/lib/*.server.ts Server The .server in the name makes the build refuse to send the file to a browser.
app/routes/api.*.ts Server These files have an action and no component at all.

One page load, in seven steps

  1. Browser sends a request for an address, such as /.
  2. Server finds the address in the route table, app/routes.ts, which names a route file.
  3. Server runs that file's loader.
  4. Server The loader calls a service, which sends a query to the database.
  5. Database returns rows.
  6. Server runs the component with the loader's result and sends back finished HTML.
  7. Browser shows the HTML, downloads the JavaScript, and runs the component again (hydration).

Three ways to check for yourself

Where did this line run?

Put a console.log("HERE") on it and reload the page. If it prints in the terminal, it ran on the server. If it prints in the browser console, it ran in the browser. Many lines do both.

What did the server send?

Ctrl+U shows the page source: the HTML exactly as it arrived, before any JavaScript ran in the browser.

Is it code or data?

Run git status. Code changes show up there. Changes to the data never do, because data.db is left out of git.

The warning sign in a diff

Server code heading for the browser. Look for a file in app/components/ that imports from ~/services/…, or a route file that calls a service function anywhere other than inside its loader or action. A route file importing a service at the top is normal: that import is for the loader.
