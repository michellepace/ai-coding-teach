Lesson 2

What happens when you press Save?

In lesson 1 you typed Testing into the admin page, pressed Enter, and the home page went from 5 categories to 6. Lesson 1 followed a number out of the database. This lesson follows a change in.

What you will be able to do

  • Trace a save from the keypress in the browser to the new row in data.db, and back to the refreshed page.
  • Say in which order the action, the loader and the component run after a save, and why.
  • Use the words action, intent, fetcher and revalidation when you ask Claude for a feature that saves something.

Why this comes next

The star-ratings lesson: file 06.1 in lessons/04-fundamentals/ of your course repo.

Every feature the course has Claude build from here on saves something: a star rating, a comment, an answer. Each one is a copy of the journey on this page, with different names. Once you can read this one, you can read Claude's diff for any of them and say which part is missing.

Reading and writing are twins

A route file can export two special functions. You met one in lesson 1. The loader reads: it fetches what the page needs. The action writes: it takes a change the browser sent and saves it. Both live in the same file, and both run only on the server.

Data mutations are done through Route actions. When the action completes, all loader data on the page is revalidated to keep your UI in sync with the data without writing any code to do it.

React Router, Actions
Mutation is the docs' word for a change to the data: an insert, an update or a delete. Revalidated means "the loader was run again".

Two new words in that sentence, and both will come up again. The second one is the whole trick of this lesson: after a save, you never write code to refresh the page. The loader simply runs again.

Follow the Testing

You are Alex Rivera, the admin, on localhost:5173/admin/categories. You have clicked Add Category, typed Testing, and you press Enter. Here is everything that happens next. Every excerpt is real code from your repo, with its line numbers.

The order to remember, because the quiz asks:

What Where it runs What it does
fetcher.submit(…) in the component Browser only Sends a POST request carrying the form data
The action function in the route file Server only Checks who is asking, reads the form data, calls a service
The service, such as createCategory Server only Runs the INSERT against data.db
The loader, run again (revalidation) Server only Fetches the fresh list, automatically
The component, run again, and its effect Browser only Redraws the table, shows the toast

When the save fails

Try to add Design a second time and a red toast says A category with the name "Design" already exists. You have already read that sentence: it is line 60 of the service, on the server. The service throws it, the action catches it on line 96 and sends it back as an error with status 400, and the effect on line 147 shows it. Nothing was written, so the loader does not run again. Three places took part in one error message, and the words were chosen in the service.

The same shape, seventeen times

To see them: Ctrl+Shift+F in the course repo, search export async function action.

Seventeen route files in app/routes/ export an action, and almost all follow this shape: check the user, read the form data, branch on intent, call a service, return a result. So when Claude builds a feature that saves something, expect its diff to touch three things: a service function that writes, an action (or a new intent in an existing one) that calls it, and a fetcher or form in the component that submits. If one of the three is missing, ask where it is.

    I have predicted and looked. Show me what should have happened.

    Terminal: ACTION RAN, then LOADER RAN. The action saved, then the loader was run again without anyone asking. Browser console: neither. Both functions live on the server.

Check yourself

Five questions. Answer from memory without scrolling up. Your first answer to each is the one that counts.

You press Enter on a new category and the save succeeds. In what order do these three run?

  • Loader, then action, then component
  • Action, then loader, then component
  • Component, then action, then loader

The action saves the change. React Router then runs the loader again so the page's data is fresh. Last, the browser runs the component with the new loaderData. That is the ACTION RAN, LOADER RAN order you saw in the terminal.

Claude's diff deletes the admin check from action (lines 75 to 78), with the note "the loader already checks this". Why is that wrong?

  • The loader runs after the action, so its check comes late
  • The action runs in the browser, where the loader cannot check
  • A POST can arrive without the page, so each must check

A POST request can be sent straight to /admin/categories by anything, without the page ever loading. The loader's check guards reading the page; the action's check guards changing the data. Both run on the server, and each needs its own lock.

Where does handleSave, the function that calls fetcher.submit(…) on line 154, run?

  • In the browser only
  • On the server only
  • In both, server first

handleSave runs when a key is pressed or a button is clicked, and clicks only happen in a browser. It is the sending end. The receiving end, the action, is the part that runs on the server.

A red toast says A category with the name "Design" already exists. Which place chose those words?

  • The browser, inside the component's effect
  • The server, inside the category service
  • The database, as a uniqueness error

Line 60 of categoryService.ts builds that sentence and throws it. The action catches it and returns it as error; the component's effect only displays it. The database never saw the duplicate: the service checked first.

Claude replaces fetcher.submit(…) in handleSave with a direct call, createCategory(trimmed). Why is that a mistake?

  • handleSave runs on the server, so the fetcher is lost
  • handleSave runs before the loader, so the table stays stale
  • handleSave runs in the browser, which can never open data.db

handleSave is browser code, and createCategory uses db, the server's open connection to data.db. The browser has no such thing. Database writes belong in the action, which is why the component submits instead of calling. This is the same mistake as lesson 1's last question, in its most common disguise.

Words to use with Claude

You can now put these in a prompt or a review comment, and Claude will know exactly what you mean. All of them are in the glossary.

Word Use it like this
action "Put the save in the route's action, not in the component."
intent "Add a rate intent to the existing action rather than a new route."
fetcher "Submit it with a fetcher so the page does not navigate away."
service "The insert should live in a service function, and the action should call it."
revalidation "You do not need to refetch the list after saving; revalidation does that."
mutation "Which of these changes is a mutation, and which is just a read?"
